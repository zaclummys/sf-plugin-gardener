# Gardener rules

Catalog of static analysis rules for Salesforce DX projects.

A rule that anticipates a limit Salesforce already enforces carries a **Reference** line with the link to the official documentation. The goal is to fail at lint and not at deploy, when fixing costs a lost cycle or rework in production.

## Catalog organization

The catalog is organized in vertical slices. Each rule lives in the file of the metadata type it checks, next to the rules that complement it. Anyone working with a type reads everything about it in one place.

The origin of a rule does not create a file. Platform limit, maintainability and security are examples of origin. The origin appears as data on the rule itself, such as the **Reference** line on rules that anticipate a Salesforce limit.

A rule name has the form `type/rule`, where `type` is the kebab-case name of the file that holds the rule.

Each type is a single metadata type of the Metadata API, and a file never groups several types. When the same rule applies to more than one type, each type gets its own copy of the rule, and the copies after the first say "Same as" and point to the first.

Each rule shows a status. A rule is implemented when its file exists in `src/rules`, and planned otherwise.

Rules that do not belong to a type live in Project structure rules. A new rule goes into the file of the type it measures. The file is created only if the type does not exist yet.

## Common configuration

Each rule is a section and lists under `Properties` everything it accepts in the configuration. A property with no description in the rule itself has the meaning defined here.

- `severity`: `error`, `warn` or `off`. Every rule accepts this property.
- `allowlist`: list of components exempt from the rule. Each item is an API name or, in its absence, a file path. Items accept glob.
- `max`: integer numeric limit, required and with no built-in default value, because the limit varies by project, by org edition and by API version. The rule text says what is measured. In rules with a **Reference** line, the value is usually the official platform limit.
- `allowedDomains`: list of accepted email domains.

Each rule ends with an example of its entry in `rules`. The entry value is a severity or, when the rule has other properties, an object. File and format names are illustrative.

The numbers in the examples are illustrative. Limits imposed by the platform must be checked in the documentation indicated in the rule's **Reference** line, because Salesforce may change them without notice.

## Criteria for promoting a property to a rule

A property becomes its own rule when it passes at least one of the tests below.

1. **Independent severity.** Two behaviors that need different severities are two rules, because a single `severity` cannot express error in one case and warning in the other.
2. **Independently switchable.** If a reasonable person wants to turn one behavior off and keep the other, they are two rules.
3. **Detects something else.** A property that changes what is detected, and not the limit, the scope or the list of values, is a rule. The classic sign is a boolean that turns on a variant.

What stays a property is whatever only tunes an existing detection. This includes limits such as `max` and `minLength`, lists of values such as `forbiddenSuffixes`, scope such as `objects` and exemptions. The `allowlist` is never promoted.
